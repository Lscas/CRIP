# Project questions — FR-QA-001

The reviewer asks an English question about the project without selecting an Analysis Run. CIRP automatically uses the newest saved `PARTIAL` or `COMPLETED` analysis for that project, performs a bounded deterministic search over its immutable parser/OCR evidence, then sends only the top evidence windows and the question through the existing configured low-cost model gateway. The local SQLite FTS5 index covers source text, file name and readable Section/Sheet/Page/Paragraph locators. Exact RFI/Submittal identifiers and Email header/body terms therefore compete by relevance instead of database insertion order. Project and run scope are checked by the server; evidence from another project is never eligible. The Analysis Run selector remains only for reviewing historical snapshots.

Analysis evidence, review records and settled question responses are already stored in the local database. `/api/projects/{project_id}/knowledge` reports the current saved knowledge snapshot without exposing evidence text: it identifies the latest usable run, whether an analysis update is active, and whether newly uploaded files are excluded. A newer terminal analysis automatically becomes the default for subsequent questions. Until then, the browser labels older saved knowledge as out of date instead of silently claiming that new files were included. The API still accepts an explicit `run_id` for compatibility and enforces the same project boundary.

Question retrieval expands at most 10 extracted user terms plus recognized complete workflow phrases into at most 24 audited search terms. Narrow construction and workflow groups cover common inflections plus accepted/approved, answer/reply/response, Email/message/correspondence, specification/spec, quantity/qty, dimensions/size, and complete phrases such as `Request for Information`/`RFI`, `Shop Drawing`/`Submittal`, and `Product Data`/`Submittal`. Expansion never adds an opposite disposition such as rejected. Whole-word boundaries prevent accidental matches such as `size` inside `oversized`; a direct user-term match scores above an expanded equivalent.

An explicitly written pure-numeric RFI identifier receives the same leading-zero normalization already used by the parser and workflow reviewer. `RFI 42` and `Request for Information No. 0042` therefore share a canonical local identity. The primary 24-term query remains unchanged; only this explicit case adds a second local FTS query containing at most 24 complete RFI phrase variants and returning at most 12 supplemental candidates. The local ranker verifies the full workflow phrase so a page number or unrelated `42` cannot outrank the canonical RFI. A complete-scan compatibility runtime applies the same identity locally. Bare numbers, compound or prefixed RFI identifiers such as `42-1` and `ARC-0042`, and Submittal identifiers remain exact and never receive this expansion. No provider request is added.

Source diversity is conditional rather than global. It activates when the question uses an explicit comparison word or names at least two of Drawing, Specification, RFI, Submittal and Email. The normal top candidates are supplemented by small, independently bounded searches for the source families named in the question; an unspecified comparison checks all five. This prevents more than 160 repeated specification fragments from hiding a later drawing or RFI before local ranking. Email supplementation covers native `.eml`/`.msg`, explicit Email locators, and generically named evidence whose first visible header is `From:`, `To:`, `Cc:` or `Subject:` and whose text contains a Subject header. RFI and Submittal supplementation also recognizes exact line-leading `RFI`, `Request for Information`, `Submittal` and `Submission` headings at the start of a generically named fragment or after a newline. This keeps printed/exported Email and workflow forms eligible even when their filenames and first lines are generic. The ranked set then contributes the best passage from each distinct document/workflow family before lower-ranked passages from an already represented source fill the remaining slots. This also separates exact workflow sections inside one combined document. Ordinary single-source questions keep the unmodified relevance order. Before either mode applies the eight-passage and 18,000-character prompt limits, exact repeated source text in the same document, source family and semantic Section/Sheet/Paragraph scope contributes only once. The same text remains eligible when it comes from another document or another semantic scope; a Page number alone is a physical locator rather than a new semantic passage.

Fragment assembly now keeps nearby native source text together without treating proximity as proof. From each of at most eight matched document pages, CIRP may add at most three closest non-vision fragments. Those siblings become eligible context but receive no relevance boost, so an exact RFI, Sheet or Paragraph match remains ahead of generic adjacent text. For an explicitly named Sheet or Drawing, an exact retained visual Sheet locator may route the local search to at most eight matching document pages and 40 native fragments per page. The visual narration itself never enters the answer context and cannot support the Sheet identifier or any project fact. Long native fragments use bounded windows around multiple matched concepts instead of only the first match; the combined window remains at most 2,600 characters while exact quotations are still checked against the complete immutable fragment.

An answered comparison must keep its conclusions auditable by source. For every source family explicitly named in the question, the model returns a separate plain-English finding with that source's readable type, exact file name and one or two exact quotations from the same file and type. The server rejects an answered comparison that omits a requested family, labels a citation with the wrong source type or file, cites evidence outside the retrieved set, or changes the source text. A standard CSI Section locator such as `Section 22 11 16` identifies Specification evidence even when the containing file has a generic name. An explicit Drawing/Sheet/Dwg/Detail identifier or plural Drawings/Sheets/Plans/Plan Set phrase requests the Drawing family; a generic singular lookup such as `Which sheet applies to RFI 42?` remains an ordinary RFI question. An exact Sheet locator, native CAD extension, explicit drawing file name or line-leading drawing marker identifies Drawing evidence only after Email, RFI, Submittal and Specification checks. `Shop Drawing` remains a Submittal phrase unless the question separately names another drawing source. This deterministic label does not infer applicability, revision, discipline, authority or precedence. Ordinary questions continue to use the compact top-level answer and citations.

Each submission is one explicit action. Unresolved-call blocking, usage settlement, request pacing, non-reasoning policy, durable task identity and no-automatic-retry rules remain in force. The currently configured live API or local model may answer from an older terminal run's immutable evidence even when that run was analyzed with Mock or another provider; the question task fingerprint includes the current provider, model, prompt and evidence snapshot. Repeating an identical question against the same snapshot and provider recovers its settled response without another provider request. Mock mode performs local retrieval only and states that no answer was generated.

Every response exposes its execution route as `answer_basis`. `WORKFLOW_INDEX` and `LOCAL_PROJECT_EVIDENCE` are deterministic no-model paths. `MODEL_PROJECT_EVIDENCE` is a model-produced answer that passed the existing project-evidence validation; `cached=true` means the current submission reused a settled response and made no new model call. `RETRIEVAL_ONLY` is Mock retrieval without generation, and `NO_MATCHING_EVIDENCE` means retrieval found no matching project evidence. The browser renders this route as an English badge before the answer. The badge adds no retrieval, provider request, retry or budget action and is not an independent claim of engineering correctness.

`ANALYSIS_INCOMPLETE` is a pre-retrieval fail-closed path. If any selected document has a terminal `FAILED` parser result, CIRP publishes no project answer, source passage or deterministic workflow result and makes no model call. The user must select or create a run in which the failed file parses successfully. A merely `PARTIAL` run remains eligible under the existing coverage and review rules; this gate is limited to explicit document failure.

Question task identity collapses only repeated whitespace. The original submitted wording is still sent to the configured model and returned to the page; letter case, punctuation and other content remain significant so case-sensitive model numbers and asset labels cannot share a result accidentally. A settled task produced before whitespace normalization is still checked under its prior exact identity before any request. Once a normalized task exists, equivalent spacing variants recover it without another provider call or budget reservation.

An exact unfiltered plural inventory question such as `How many RFIs, Submittals, and Emails are in this run?` or `List all RFIs, Submittals, and Emails in this run.` reuses the complete cached workflow index before evidence retrieval. It returns `ANSWERED` with `answer_basis=WORKFLOW_INDEX`, zero retrieved passages, no model call and no budget action. RFI and Submittal inventory counts exact identifier groups, including reference-only identifiers whose primary source still needs review. Email inventory deduplicates analyzed documents classified as Email or retained as `.eml`/`.msg` members after a manual workflow correction; an attachment is not included unless it was explicitly imported and analyzed. A list reports the complete total for each requested category and exposes at most the first 50 ordered values; the existing paginated Workflow Reviewer remains the complete large-inventory view. The shortcut accepts only complete count, list, show, which or what forms for the plural categories. Identifier, source-document, date, content and multi-filter questions—such as `How many RFIs were open last month?`, `List RFI documents.` or `List RFIs mentioning concrete.`—remain on the ordinary evidence path because a run-wide inventory cannot answer them safely.

A strict status-filtered inventory question such as `How many open RFIs are in this run?`, `How many RFIs are open?` or `List all approved as noted Submittals in this run.` now uses the same complete index when its filter is one disposition already recognized for every requested workflow type by the bounded parser. An inapplicable combination such as approved RFIs or closed Submittals remains on the ordinary evidence path instead of returning a misleading deterministic zero. Only an identifier with one distinct explicit detected-or-manually-corrected primary status supporting the filter enters the confirmed count or list. An identifier containing a matching status plus another explicit status is excluded from that result and reported separately as ambiguous. A missing response, relationship state, reference-only identifier or absent status never manufactures a match. Existing conservative equivalents remain aligned: `OPEN FOR REVIEW` supports `OPEN`, `SUBMITTED` supports `PENDING`, and `APPROVED AS NOTED` supports broad `APPROVED`, while the qualified `APPROVED AS NOTED` filter does not accept plain approval. RFI/Submittal contexts parsed from Email participate; Email messages themselves do not receive a semantic workflow status. Lists report complete confirmed and ambiguous totals and expose at most 50 values from each set per category. Other status prose or additional filters stay on the ordinary evidence path.

A strict direct question such as `What is the status of RFI 42?`, `Tell me the disposition for Request for Information No. 0042.` or `What status does Submittal 23 05 00 - 01 have?` also checks the complete workflow index before retrieval. If the exact identifier has one distinct explicit primary status from the bounded vocabulary applicable to its workflow type, CIRP returns it locally with `answer_basis=WORKFLOW_INDEX`, zero retrieved passages and no provider or budget action. Every status source is rendered immediately below the answer with its original file link and detected/manual origin. An automatically detected source receives the same bounded exact parser-text quotation used for conflict provenance only when that phrase is tied to the same normalized identity; a manual correction remains visibly file-only. Multiple source statuses or one malformed multi-state value such as `OPEN CLOSED` remain insufficient evidence. If the exact item has no explicit indexed status, an unknown value or a status inapplicable to that workflow type, the question stays on the ordinary evidence path so CIRP does not turn absence or invalid legacy metadata into a status. Comparisons, explanations, yes/no predicates, additional filters and Email-thread status questions are outside this deterministic shortcut.

The model may return `ANSWERED` only with at least one top-level citation or one cited source finding from the supplied evidence. Every published quotation must match the immutable source text exactly and uniquely; an invented quote, unknown evidence ID, truncated response, invalid JSON, or out-of-contract field fails closed after accounting and is never silently retried. A terminal answer failure stores only a stable bounded diagnostic category such as `citation_scope`, `exact_quote`, `numeric_support` or `calculation`, never the provider response or evidence text. Project evidence is treated as untrusted data, not as instructions. The page renders answer and finding text without HTML and puts each source quotation directly below the finding it supports, with a link to the existing evidence viewer.

Explicit numeric claims receive an additional deterministic check. Every number in an answered top-level summary must be present in at least one of its top-level or nested exact quotations, and every number in a source finding must be present in that finding's own quotations. Formatting-only thousands separators, leading-zero and trailing-decimal-zero differences are normalized. A comma is treated as a thousands separator only in valid three-digit groups, so a source list or coordinate such as `1,2` cannot support a claim of `12`.

One narrow exception supports questions that explicitly ask to calculate, compute, add, subtract, multiply, divide, sum, total or find a percentage. The model must declare each `ADD`, `SUBTRACT`, `MULTIPLY` or `DIVIDE` step in a structured calculation list and repeat the operation in the plain-text answer. CIRP independently recomputes every step with decimal arithmetic. Every first-step operand must be an exact non-date, non-workflow-identifier, non-spec-section, non-drawing-label and non-clause numeric literal from the cited source text; later steps may use a prior verified result. Percent operands are limited to multiplication or division. Results must be exact and present in the answer. Source findings remain fully quote-bound. Unit conversion, date arithmetic, rounding, geometry inference and engineering interpretation remain prohibited, so any result requiring those operations returns `INSUFFICIENT_EVIDENCE` or fails the contract after usage settlement.

An ordinary answer or source finding that attaches a non-identifier number to an RFI/Submittal also preserves that exact relationship. The normalized workflow identity and number must occur in one cited statement, or a statement without an identity may use a citation locator containing exactly that one matching identity. `RFI 42 response: Use 2 inch pipe. RFI 43 response: Use 4 inch pipe.` therefore cannot support `RFI 42 requires 4 inch pipe.` A locator naming both items cannot resolve the relationship. Pure-numeric RFI zero padding remains equivalent, while numbers inside the workflow identifier are excluded from this property check. Each source finding in a comparison is checked independently; its top-level comparison summary may combine only those validated findings. CIRP does not infer units, bind a number to a particular property name, calculate a delta or decide which source controls.

When citations explicitly distinguish measurement properties, CIRP also keeps each number with its mutually nearest property label. Size, diameter and dimensions normalize to `SIZE`; thickness, length, width, height, depth, quantity, pressure, strength, flow, capacity, temperature and weight remain separate. A dimensional number next to pipe, tube, duct, conduit or opening may conservatively supply `SIZE`, while insulation, membrane, coating or liner may supply `THICKNESS`; otherwise an absent role is not invented. `Pipe diameter is 2 inch. Insulation thickness is 1 inch.` cannot support a 1-inch pipe-diameter answer, and an RFI/Submittal identity, property and number must remain together. This bounded lexical guard does not understand arbitrary engineering properties, convert units, calculate dimensions or decide contractual precedence.

Recognized measurement units add one more relationship check. Every explicit number/unit pair in an ordinary answer or source finding must occur in its own citations. When a recognized property and RFI/Submittal identity are present, the complete identity/property/number/unit combination must also occur together; independent partial matches cannot be recombined. `Pipe diameter is 2 inch. Insulation thickness is 2 mm.` therefore cannot support a 2-mm pipe diameter, even though every token appears in the quotation. Recognized alphabetic units may be spaced or compact (`2 mm`/`2mm`, `150 MPa`/`150MPa`, `4 L/s`/`4L/s`). Inch, inches, `in.` and straight/typographic quotation marks normalize together; feet, foot, `ft` and apostrophe marks do likewise. Millimeter, centimeter, meter, PSI/kPa/MPa/bar, GPM/CFM/LPM/L/s, percent, pound/kilogram/ton and explicit Celsius/Fahrenheit units remain distinct. Bare `in` is not treated as a unit because it is also ordinary English. CIRP performs no unit conversion.

Explicit six-digit CSI/MasterFormat sections are also checked as complete values before their component numbers. `Specification Section 22 11 16` and `Specification Section 23 05 00` cannot be recombined into an unsupported `Section 22 05 16`. Spaces, hyphens and dots between the three two-digit groups normalize as formatting only, and an immediate two-digit extension such as `.13` remains part of the section. A section may come from the exact quotation or its evidence locator. If an answer names an RFI or Submittal, that workflow identity and section must occur in the same cited statement or one exact locator; another workflow item cannot donate the section. Unlabelled strings such as `Submittal 23 05 00 - 01` remain workflow identifiers rather than section claims. The guard does not infer unlabelled codes, specification applicability or contractual precedence.

Explicit Revision/Rev labels receive the same atomic and workflow-scoped treatment. A citation stating `RFI 42 ... Revision A` and `RFI 43 ... Revision B` cannot support `RFI 42 ... Revision B`; `Revision A1` and `Revision B2` cannot support a recombined `Revision A2`. Prefix forms such as `Revision A`, `Rev. A`, `Revision: IFC`, `Rev IFC`, `Revision No. P2` and `Rev: P2` normalize only the prefix punctuation and letter case. Single letters, numeric or digit-bearing codes, and explicit `IFC`, `IFB` and `AS BUILT` labels remain exact values. Revision-date wording and unlabelled status words are excluded. Numeric revision labels are validated here rather than treated as quantities. The label must be written in the cited text; evidence metadata alone does not support a claim, and CIRP does not infer chronology, applicability or which revision controls.

Explicit Sheet/Drawing/Dwg/Detail identifiers are also atomic and workflow-scoped. A citation containing `Sheet A1.01` and `Sheet P2.02` cannot support a recombined `Sheet A1.02`; similarly, `Detail 3/A5.1` and `Detail 5/A7.2` cannot support `Detail 3/A7.2`. One RFI, Submittal, Email-derived workflow context or comparison finding cannot donate its drawing identifier to another. Prefix spelling/punctuation, letter case and en/em dash glyphs normalize, while the identifier's letters, digits, dots, slashes and separators remain exact. An exact `Sheet` evidence locator may support the corresponding identifier even when the quoted schedule title omits it. Numeric sheet/detail identifiers are validated here rather than treated as quantities. Unlabelled codes and date-shaped values are excluded, and CIRP does not infer drawing applicability, discipline, revision, contractual authority or precedence.

Explicit dotted Paragraph/Para, Clause and Article identifiers receive the same atomic and workflow-scoped treatment. `Paragraph 2.3.1` and `Paragraph 4.5.6` cannot support `Paragraph 2.3.6`, and one RFI, Submittal, Email-derived workflow context or comparison finding cannot donate its identifier to another. Paragraph and Para plus prefix punctuation and letter case normalize, while Paragraph, Clause and Article remain distinct typed references and the dotted value remains exact. An exact Paragraph locator may support its corresponding Paragraph identifier when the quotation omits it. The bounded parser accepts two to six dot-separated numeric groups with an optional terminal letter; unlabelled values, undotted values, date-shaped values, hierarchy and applicability remain outside the claim path.

Explicit conventional email addresses are atomic, role-aware and workflow-scoped. A citation containing `From: architect@example.test` and `To: owner@project.test` cannot support `architect@project.test`, cannot call the owner address the sender, and cannot donate either address to another RFI, Submittal or source finding. Domain letter case normalizes while the local part remains exact. The bounded parser recognizes ASCII dot-atom local parts with dotted DNS-style domains plus explicit From, To, Cc, Bcc and Reply-To headers or immediate sender/recipient prose. Quoted local parts, domain literals, SMTPUTF8, undotted internal domains, mailbox ownership, thread participation, identity equivalence and authority remain outside this guard.

Explicit Email participant display names are atomic and role-aware within Email-classified citations. `From: Alice Architect <alice@example.test>` and `To: Bob Builder <bob@example.test>` cannot support `Email sender: Bob Builder`, `Email sender: Alice Builder` or a name borrowed by another source finding. The bounded parser reuses Python's standard-library mailbox parser for display names attached to conventional addresses and accepts one bounded name-only printed header value. From, To, Cc, Bcc and Reply-To remain distinct. Case, repeated whitespace and outer quotation marks normalize; the complete name otherwise stays exact. When a sender/recipient question is answered from Email evidence, the answer or corresponding finding must explicitly state the supported role value as a display name or already validated address. Line-leading header labels are required, so ordinary wording such as `According to:` is not a recipient claim. RFI/Submittal-form From/To fields, encoded-header recovery, folded-header recovery, address-to-name identity, company/title/signature inference, thread position and authority remain outside this guard.

Explicit Email Date-header claims are atomic and source-local. A citation with `Date: January 5, 2024` and `Received: January 6, 2024` cannot support `Email Date header: January 6, 2024`; two cited `Date:` headers cannot be recombined into a third timestamp. Only evidence conservatively classified as Email can ground the claim, so an RFI or Submittal form's Date field remains part of that source type. Email date and Date-header claims compare one complete line value after formatting-only case, repeated-whitespace, outer-quotation and answer-ending-punctuation normalization. The weekday, date, time, seconds, numeric offset and comments otherwise remain exact. A question asking for one or more Email dates or Date headers may return `ANSWERED` only when the answer or corresponding source finding explicitly states each complete header value. A natural question asking when an Email was sent requires the same Date-header claim or a separately labelled exact Sent date; Received and body dates cannot fill that role. The guard does not decode or unfold new source formats, convert time zones, select the current message, infer delivery/transport time or decide authority.

Explicit RFI/Submittal form Subject claims are atomic, workflow-scoped and distinct from Email Subject headers. `RFI 42 / Subject: Domestic Water Pipe` and `RFI 43 / Subject: Fire Alarm Coordination` cannot support `RFI 42 subject: Fire Alarm Coordination` or a recombined `Domestic Alarm Coordination`. One source-local Subject line binds to the nearest preceding exact workflow identifier; when the quotation contains no identifier, one exact RFI/Submittal identity in its evidence locator may supply the scope, while a multi-identity locator remains insufficient. Case, repeated whitespace, outer quotation marks and answer punctuation outside the value normalize; punctuation quoted inside the subject remains exact. A subject question naming an RFI or Submittal may return `ANSWERED` only when the answer or corresponding source finding states `<identifier> subject: <complete value>`. Separate source findings cannot borrow values, an Email Subject header cannot ground the form field, and CIRP does not infer applicability, status, revision or authority.

A strict direct question such as `What is the subject of RFI 42?`, `Show me the Subject line for Request for Information No. 0042.` or `What subject does Submittal 23-01 have?` first reuses the complete cached workflow index to identify that exact item's primary form documents. CIRP then reads only existing non-vision evidence from at most 32 such documents and at most 512 Subject-bearing passages; it does not reparse a file or build another index. One distinct normalized Subject value returns locally with `answer_basis=LOCAL_PROJECT_EVIDENCE`, its exact quotations and no provider or budget action. Multiple distinct primary-file values return `INSUFFICIENT_EVIDENCE` with all found conflicting quotations. More than either safety limit also fails closed. Email documents are excluded even when their Subject mentions the same workflow identifier. If no explicit supported form Subject is found, the question remains on the ordinary evidence-and-model path instead of treating absence as an answer. Comparisons, explanations, generic topics, multiple identifiers and Email-subject questions are outside this shortcut.

A strict direct question such as `What is the question in RFI 42?`, `What does Request for Information No. 0042 ask?` or `What is the official response to RFI 42?` also reuses the complete cached workflow index before ordinary retrieval. Current Email-body RFI scopes participate, while `EMAIL > QUOTED HISTORY` cannot donate content. When the index has no requested role or no matching parser-scoped passage, the question remains on the ordinary grounded path. Interpretive wording such as `What does RFI 42 require?`, comparisons, multiple identifiers, Submittals, status selection, chronology and controlling-source decisions are outside this shortcut.
