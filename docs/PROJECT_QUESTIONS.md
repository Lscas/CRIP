# Project questions — FR-QA-001

The reviewer may select a `PARTIAL` or `COMPLETED` analysis run and ask an English question about its files. CIRP first performs a bounded deterministic search over that run's immutable parser/OCR evidence, then sends only the top evidence windows and the question through the existing configured low-cost model gateway. The local SQLite FTS5 index covers source text, file name and readable Section/Sheet/Page/Paragraph locators. Exact RFI/Submittal identifiers and Email header/body terms therefore compete by relevance instead of database insertion order. Project and run scope are checked by the server; evidence from another project is never eligible.

Question retrieval expands at most 10 extracted user terms plus recognized complete workflow phrases into at most 24 audited search terms. Narrow construction and workflow groups cover common inflections plus accepted/approved, answer/reply/response, Email/message/correspondence, specification/spec, quantity/qty, dimensions/size, and complete phrases such as `Request for Information`/`RFI`, `Shop Drawing`/`Submittal`, and `Product Data`/`Submittal`. Expansion never adds an opposite disposition such as rejected. Whole-word boundaries prevent accidental matches such as `size` inside `oversized`; a direct user-term match scores above an expanded equivalent.

An explicitly written pure-numeric RFI identifier receives the same leading-zero normalization already used by the parser and workflow reviewer. `RFI 42` and `Request for Information No. 0042` therefore share a canonical local identity. The primary 24-term query remains unchanged; only this explicit case adds a second local FTS query containing at most 24 complete RFI phrase variants and returning at most 12 supplemental candidates. The local ranker verifies the full workflow phrase so a page number or unrelated `42` cannot outrank the canonical RFI. A complete-scan compatibility runtime applies the same identity locally. Bare numbers, compound or prefixed RFI identifiers such as `42-1` and `ARC-0042`, and Submittal identifiers remain exact and never receive this expansion. No provider request is added.

Source diversity is conditional rather than global. It activates when the question uses an explicit comparison word or names at least two of Specification, RFI, Submittal and Email. The normal top candidates are supplemented by small, independently bounded searches for the source families named in the question; an unspecified comparison checks all four. This prevents more than 160 repeated specification fragments from hiding a later RFI before local ranking. The ranked set then contributes the best passage from each distinct document/workflow family before lower-ranked passages from an already represented source fill the remaining slots. This also separates exact workflow sections inside one combined document. Ordinary single-source questions keep the unmodified relevance order. Both modes retain the eight-passage and 18,000-character prompt limits.

An answered comparison must keep its conclusions auditable by source. For every source family explicitly named in the question, the model returns a separate plain-English finding with that source's readable type, exact file name and one or two exact quotations from the same file and type. The server rejects an answered comparison that omits a requested family, labels a citation with the wrong source type or file, cites evidence outside the retrieved set, or changes the source text. A standard CSI Section locator such as `Section 22 11 16` identifies Specification evidence even when the containing file has a generic name. Ordinary questions continue to use the compact top-level answer and citations.

Each submission is one explicit budgeted action. The existing CNY project limit, unresolved-call freeze, usage settlement, request pacing, non-reasoning policy, and no-automatic-retry rules remain in force. The currently configured live API or local model may answer from an older terminal run's immutable evidence even when that run was analyzed with Mock or another provider; the question task fingerprint includes the current provider, model, prompt and evidence snapshot. Repeating an identical question against the same snapshot and provider recovers its settled response without another provider request. Mock mode performs local retrieval only and states that no answer was generated.

Question task identity collapses only repeated whitespace. The original submitted wording is still sent to the configured model and returned to the page; letter case, punctuation and other content remain significant so case-sensitive model numbers and asset labels cannot share a result accidentally. A settled task produced before whitespace normalization is still checked under its prior exact identity before any request. Once a normalized task exists, equivalent spacing variants recover it without another provider call or budget reservation.

An exact unfiltered plural inventory question such as `How many RFIs, Submittals, and Emails are in this run?` or `List all RFIs, Submittals, and Emails in this run.` reuses the complete cached workflow index before evidence retrieval. It returns `ANSWERED` with `answer_basis=WORKFLOW_INDEX`, zero retrieved passages, no model call and no budget action. RFI and Submittal inventory counts exact identifier groups, including reference-only identifiers whose primary source still needs review. Email inventory deduplicates analyzed documents classified as Email or retained as `.eml`/`.msg` members after a manual workflow correction; an attachment is not included unless it was explicitly imported and analyzed. A list reports the complete total for each requested category and exposes at most the first 50 ordered values; the existing paginated Workflow Reviewer remains the complete large-inventory view. The shortcut accepts only complete count, list, show, which or what forms for the plural categories. Identifier, source-document, date, content and multi-filter questions—such as `How many RFIs were open last month?`, `List RFI documents.` or `List RFIs mentioning concrete.`—remain on the ordinary evidence path because a run-wide inventory cannot answer them safely.

A strict status-filtered inventory question such as `How many open RFIs are in this run?`, `How many RFIs are open?` or `List all approved as noted Submittals in this run.` now uses the same complete index when its filter is one disposition already recognized for every requested workflow type by the bounded parser. An inapplicable combination such as approved RFIs or closed Submittals remains on the ordinary evidence path instead of returning a misleading deterministic zero. Only an identifier with one distinct explicit detected-or-manually-corrected primary status supporting the filter enters the confirmed count or list. An identifier containing a matching status plus another explicit status is excluded from that result and reported separately as ambiguous. A missing response, relationship state, reference-only identifier or absent status never manufactures a match. Existing conservative equivalents remain aligned: `OPEN FOR REVIEW` supports `OPEN`, `SUBMITTED` supports `PENDING`, and `APPROVED AS NOTED` supports broad `APPROVED`, while the qualified `APPROVED AS NOTED` filter does not accept plain approval. RFI/Submittal contexts parsed from Email participate; Email messages themselves do not receive a semantic workflow status. Lists report complete confirmed and ambiguous totals and expose at most 50 values from each set per category. Other status prose or additional filters stay on the ordinary evidence path.

A strict direct question such as `What is the status of RFI 42?`, `Tell me the disposition for Request for Information No. 0042.` or `What status does Submittal 23 05 00 - 01 have?` also checks the complete workflow index before retrieval. If the exact identifier has one distinct explicit primary status from the bounded vocabulary applicable to its workflow type, CIRP returns it locally with `answer_basis=WORKFLOW_INDEX`, zero retrieved passages and no provider or budget action. Every status source is rendered immediately below the answer with its original file link and detected/manual origin. An automatically detected source receives the same bounded exact parser-text quotation used for conflict provenance only when that phrase is tied to the same normalized identity; a manual correction remains visibly file-only. Multiple source statuses or one malformed multi-state value such as `OPEN CLOSED` remain insufficient evidence. If the exact item has no explicit indexed status, an unknown value or a status inapplicable to that workflow type, the question stays on the ordinary evidence path so CIRP does not turn absence or invalid legacy metadata into a status. Comparisons, explanations, yes/no predicates, additional filters and Email-thread status questions are outside this deterministic shortcut.

The model may return `ANSWERED` only with at least one top-level citation or one cited source finding from the supplied evidence. Every published quotation must match the immutable source text exactly and uniquely; an invented quote, unknown evidence ID, truncated response, invalid JSON, or out-of-contract field fails closed after accounting and is never silently retried. Project evidence is treated as untrusted data, not as instructions. The page renders answer and finding text without HTML and puts each source quotation directly below the finding it supports, with a link to the existing evidence viewer.

Explicit numeric claims receive an additional deterministic check. Every number in an answered top-level summary must be present in at least one of its top-level or nested exact quotations, and every number in a source finding must be present in that finding's own quotations. Formatting-only thousands separators, leading-zero and trailing-decimal-zero differences are normalized, but fractions, conversions, arithmetic and inferred deltas are not. A comma is treated as a thousands separator only in valid three-digit groups, so a source list or coordinate such as `1,2` cannot support a claim of `12`. A missing value fails the answer contract after accounting, so the prompt directs the model to return `INSUFFICIENT_EVIDENCE` instead of calculating or guessing. This check catches strong numeric disagreement; it does not prove that surrounding prose or contractual interpretation is correct.

Explicit full dates receive a source-local check before the numeric check. Every full date in an answered top-level summary must occur as one date in a top-level or nested exact quotation, and every full date in a source finding must occur in that finding's own quotations. ISO forms such as `2024-01-05`, English month-name forms such as `January 5, 2024`, `Jan. 5, 2024`, and `5 January 2024`, and formatting-only leading zeros normalize to the same date. Slash dates normalize leading zeros but preserve written order, so `01/05/2024` can support `1/5/2024` but not `2024-01-05`; CIRP does not guess the locale. This prevents a model from recombining the components of `2024-01-05` and `2024-02-10` into an unsupported `2024-01-10`. The check does not validate calendar legality, calculate deadlines, compare chronology, choose the controlling document or cover incomplete month/year and relative-date phrases.

Supported date roles add a second source-local check. Due, issued, submitted, received, sent, reviewed, approved, revision and response wording immediately associated with a full date—or present in a sentence containing only that one full date—must retain the same role/date pair in one citation. Separate quotations cannot contribute the label and date independently. If the cited answer scope contains more than one date for the claimed role, CIRP returns insufficient evidence instead of choosing by position. A date question may report an explicitly labeled approval date from a record that also contains a submitted date because it is describing one lifecycle event, not declaring the current status. A status/disposition question against the same record keeps the existing ambiguity guard. The validator does not order events, infer a current state, or decide which source controls.

An explicit RFI/Submittal date adds exact workflow scope to that pair. The normalized identity, role and date must occur in one cited statement. When the statement omits the identifier, CIRP accepts the pair only if that citation's Section locator contains exactly one matching workflow identity. A quotation naming `RFI 42` as issued and `RFI 43` as due cannot support an `RFI 42` due-date answer; a locator naming both is also insufficient. Separate statements giving RFI 42 and RFI 43 their own due dates remain independently answerable instead of becoming globally ambiguous. Pure-numeric RFI leading zeros reuse the parser's exact equivalence; prefixed, compound and Submittal identities remain exact. Several dates for the same normalized identity and role still fail because no chronology or authority rule chooses one.

Explicit workflow identifiers receive a separate source-local check. Every normalized RFI/Submittal identity named in an answered top-level summary must occur in a top-level or nested exact quotation or that citation's Section locator, and every identity named in a source finding must occur in that finding's own quotations or locators. `RFI 42` and `Request for Information No. 0042` are the same pure-numeric identity, while `RFI ARC-42`, `RFI ARC-0042`, compound IDs and distinct Submittal IDs stay exact. Multiple workflow markers on one line are collected separately instead of letting the first marker consume the remainder. A matching locator may ground numeric occurrences inside that exact workflow ID when the quoted fragment is already scoped to it; every occurrence outside the identifier remains subject to the unchanged exact-quotation rule even when it has the same value. This blocks a model from assembling `RFI 43` out of an `RFI 42` citation plus an unrelated detail or coordination number.

Explicit workflow dispositions receive a parallel deterministic check. A bounded list follows the parser's known RFI/Submittal states and conservative wording equivalents: accepted/approved, resolved/closed, under review/pending, not approved/rejected, plus explicit open, answered, submitted, draft, void and revise-and-resubmit forms. An answered top-level disposition must occur in its cited quotations, while each source finding is checked only against its own quotations. Longer phrases win over embedded words, so `not approved` is rejection rather than approval and `approved as noted` retains both its approval and qualifier. A plain approval cannot support the added `as noted` qualifier. An opposite or unsupported state fails after cost settlement and is never retried. This is lexical contradiction prevention, not chronology, authority or contractual interpretation.

The same bounded vocabulary also preserves ambiguity inside the evidence supplied to one answer. Distinct primary states in top-level citations or in the matching retrieved evidence for one explicit workflow identity fail an answered response even if the model omits one of them from its citations. Source findings check all retrieved evidence from their own readable type and file, optionally narrowed by an explicit identifier. A recognized composite phrase such as `OPEN ANSWERED`, `OPEN WAITING FOR SUBMISSION` or `CLOSED-DRAFT` remains one state, while separate `APPROVED`/`APPROVED AS NOTED` and `PENDING`/`SUBMITTED` sources remain distinct. Different exact RFI/Submittal identifiers and separate comparison findings do not conflict with each other. CIRP returns no winner because the bounded evidence has no deterministic revision chronology or authority rule.

An exact RFI or Submittal status question also reuses the complete deterministic workflow index already cached for a terminal run. If primary sources anywhere in that index carry more than one explicit status for the requested identifier, CIRP returns `INSUFFICIENT_EVIDENCE` before Mock/live/local model dispatch, even when one source is outside the eight retrieved passages. The answer states each conflicting status, source file and whether the classification was detected or manually corrected; the page renders the same structured pairs directly below the answer with links to the original files. File names are plain text, internal document IDs are not displayed, and more than three files for one status are summarized in the answer while remaining available in the inline source list. This adds no evidence scan, provider request, budget reservation, dependency or second index. Ambiguity caused only by duplicate Question/Response sources with one consistent status does not block the question. Workflow contexts parsed from Email participate exactly like other sources; a generic Email-status question without an exact RFI/Submittal identifier remains limited to the retrieved evidence because the index intentionally does not infer a semantic status for an Email thread.

For up to 32 automatically detected conflict sources, CIRP performs one local run-and-document-scoped evidence read after the conflict is known. A source receives an inline exact quotation and its existing page, sheet, section, paragraph, line or crop locator only when the same longest bounded disposition phrase is in a statement naming the normalized requested workflow identity, or the surrounding fragment or locator is scoped to that identity alone. A status phrase naming another RFI or Submittal is never borrowed. `APPROVED AS NOTED` therefore cannot be reduced to a plain approval citation. Model-vision narration is excluded. A manual classification correction never receives a parser-text citation, and a detected status inferred only from file-level metadata remains visibly file-only when no exact phrase exists. All sources retain their original-file link. The 32-source ceiling bounds the local read; additional sources remain listed without fabricated quotations.

Existing databases are backfilled when the application first opens them, and new evidence is indexed in the same local transaction path. If the bundled SQLite runtime lacks FTS5, application startup and Q&A remain available through a complete LIKE scan; that compatibility path is slower but does not restore the old first-160-row cutoff. The index is local, adds no provider request, and is not a second hosted service.

This slice is independent-question Q&A, not a persistent conversation or a semantic vector index. Deterministic lexical ranking remains intentionally conservative; exact identifiers and project terminology work best. A grounded answer still requires human review and does not prove completeness, design correctness, or contractual authority.

## Offline acceptance evidence

- Specific construction terms rank the matching run-scoped evidence above unrelated passages.
- A precise RFI response after 160 earlier common-term passages remains the first result; Submittal identifiers, Email metadata and drawing Sheet locators are covered.
- A pre-index database is backfilled on open, and an environment without FTS5 uses the complete compatibility scan instead of silently losing later evidence.
- A 12,000-fragment padded-RFI production-path benchmark measured about 279.0 ms per complete compatibility scan versus 31.2 ms with FTS5 retrieval (about 8.94x). The same fixture's two-family comparison path measured about 87.4 ms; all three paths recovered the final `RFI 0042` passage queried as `RFI 42`. Results vary by computer and corpus.
- Bounded equivalence tests recover late `Approved as noted`, RFI response and Email sender passages from questions using accepted, answer/reply and sent, while whole-word ranking rejects `size` inside `oversized`.
- A padded `RFI 0042` Specification reference and a full-name `Request for Information No. 00077` Email response survive 160 stronger generic candidates. FTS and complete-scan paths agree; bare numbers, `RFI ARC-42`, `RFI 42-1` and Submittal IDs remain outside zero-padding equivalence.
- A comparison fixture with ten higher-scored specification passages still supplies Specification, RFI, Submittal and Email evidence; another fixture proves a combined document retains its later RFI after 200 higher-scored Specification fragments. A non-comparison fixture keeps all eight results from the more relevant specification source.
- A comparison answer missing its named RFI finding fails closed; a complete Specification/RFI answer returns both findings with exact nested citations and recovers from the settled cache without a second request.
- A mislabeled Email finding citing Specification evidence is rejected, while a generic PDF section located at `Section 22 11 16` is accepted as Specification evidence.
- An ordinary 4-inch answer cited only to a 2-inch requirement and a 4-inch Specification finding cited only to a 2-inch quotation both fail the numeric evidence contract.
- Formatting-only `4000`/`4,000` and `RFI 42`/`RFI 0042` pairs remain valid without treating arithmetic or unit conversion as evidence.
- Comma-separated source values such as `1,2` cannot be collapsed into an unsupported `12` claim.
- RFI `CLOSED` cannot be answered as open, Submittal `REJECTED` cannot be answered as approved, and an Email `PENDING` status cannot be answered as approved. Parser-aligned equivalents such as resolved/closed, accepted/approved, under review/pending and not approved/rejected remain valid; plain approval cannot manufacture an `approved as noted` qualifier.
- A comparison cannot swap an RFI and Submittal disposition between otherwise valid source findings because every finding is checked only against its own exact quotations.
- An ordinary answer cannot select one of retrieved RFI open/closed, Submittal pending/rejected or Email pending/approved evidence by omitting the other citation. The same applies inside one source finding. A paid conflicting response settles once without retry.
- An exact RFI status question is blocked before model dispatch when a second conflicting Email-derived status exists only in the full run workflow index and not in the retrieved passages. The response and page show both statuses with their original Email file names and safe file links directly below the answer. The same preflight ignores a different identifier and duplicate sources that agree on one status.
- An automatically detected RFI, Submittal or Email-derived conflict source gains an exact inline quote only when its immutable parser text ties the same bounded status phrase to the exact identifier in one statement or uniquely scoped fragment/locator. Manual corrections, another workflow's status and detected summaries without a matching original phrase stay file-only; no quote is invented. Approval versus approved-as-noted specificity is covered.
- Exact unfiltered plural inventory questions return complete workflow-index counts or bounded lists for RFI identifiers, Submittal identifiers and unique analyzed Email files without evidence retrieval or a model request. Lists retain complete totals and expose at most the first 50 ordered values per category. Status-filtered, document/source, identifier-specific and content-filtered questions do not enter this path.
- Strict one-status RFI/Submittal inventory questions count or list only identifiers with one matching explicit status. Matching identifiers with another explicit status are excluded and reported separately as ambiguous; missing documents, reference-only groups and relationship state cannot create a status. Email-derived workflow contexts participate, qualified approval stays exact, and confirmed/ambiguous lists retain totals with a 50-value ceiling each.
- Distinct status qualifiers and phases remain distinct: separate `APPROVED`/`APPROVED AS NOTED` and `PENDING`/`SUBMITTED` evidence is ambiguous, while one exact composite such as `OPEN WAITING FOR SUBMISSION` or `CLOSED-DRAFT` remains valid. `RFI 42` does not inherit `RFI 43`, and `Submittal 23-01` does not inherit `23-02`.
- The same ordinary question with repeated spaces reuses one settled provider response; a synthetic pre-normalization exact task also recovers without HTTP.
- Mock mode publishes retrieval context without a model call or fabricated answer.
- MockTransport live-provider tests answer from a Mock-analyzed evidence snapshot, settle usage, recover an identical question without another request, and reject an invented quote after recording the terminal contract failure.
- A run belonging to another project is rejected before retrieval or model dispatch.
- Browser contract validation confirms each comparison finding renders its readable source label, file name and evidence directly together, retains the existing evidence drawer action, and does not inject response HTML.

No customer document, credential, live provider, or paid API was used for this validation.
